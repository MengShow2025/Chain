# 高并发高安全设计方案（含链下撮合与验证节点防作弊）

## 目标与范围
- 目标：在维持强安全与可审计性的前提下，支持交易型业务（撮合订单、小额支付）在高并发（>10万 TPS 入口）与低延迟（<150ms 响应）场景稳定运行。
- 范围：
  - 链下高性能撮合引擎（参考 Hyperliquid 的集中式高性能序列器/撮合）与链上验证/结算的组合架构。
  - 验证节点端的确定性重放与一致性检查，以及防止“序列器/节点作弊”的制度与技术措施。
  - 小额支付/订单流的优化与安全风控策略。

## 总体架构概览
- 双层架构：
  - 入口层/撮合层（链下）：高性能撮合引擎接收订单，进行价格-时间优先队列匹配与批次压缩，形成“执行配方（Execution Recipe）”与批次承诺（Batch Commit）。
  - 验证/结算层（链上）：验证节点从上一区块状态根出发，确定性重放批次配方，校验约束与不变量；通过挑战窗口与审计日志确保数据可用与公平；最终提交状态更新与收敛结算。
- 核心思想：将“快”与“稳”分层——入口响应与撮合在链下快速完成；链上负责验证与最终性，提供可审计、可追责的保障。

## 链下撮合与验证节点执行（防作弊方案）

### 提交流程（Commit → 验证 → Finalize）
1. 客户端提交订单到撮合引擎（含签名、时间戳、序号、账户证明）。
2. 撮合引擎在固定微批次间隔（例如 50–100ms）内：
   - 根据价格-时间优先规则匹配，生成成交列表与账户余额/仓位变更。
   - 形成批次数据（Batch Data）与**执行配方**（确定性指令序列）。
   - 计算批次承诺（Batch Commit）：包括 `ordersRoot`、`matchesRoot`、`balanceDiffsRoot`、`auditLogRoot` 等 Merkle 根，及 `prevStateRoot`、`nextStateRoot` 预期值。
3. 撮合引擎广播 `BatchCommit(tx)` 到链上（或作为区块中的特殊交易），同时将完整批次数据以内容可寻址方式（IPFS/Blob）提供给验证节点。
4. 验证节点在挑战窗口内拉取批次数据，进行确定性重放与一致性检查。若通过，批次进入最终性；若发现作弊或违规，触发挑战与仲裁流程（可导致作恶方惩罚与批次撤销/重算）。

### 批次结构（建议）
- 元数据：`batchId`、`producerId`（序列器身份）、`timestamp`、`prevStateRoot`。
- 数据根：`ordersRoot`、`matchesRoot`、`cancellationsRoot`、`balanceDiffsRoot`、`auditLogRoot`。
- 执行配方（Execution Recipe）：确定性可重放的指令序列，包括：
  - 排序规则与输入集合的承诺（如时间/价格序、去重、取消继承）。
  - 匹配指令（`match(orderA, orderB, price, qty)`）。
  - 余额/仓位变更（`applyDelta(account, asset, delta)`）。
  - 不变量检查（资金守恒、仓位上下限、滑点/价格区间约束等）。
- 证明/附加：序列器签名、（可选）TEE 远程证明、独立观察者见证签名、批次数据的内容地址（CID）。

### 验证节点重放与一致性检查（核心）
验证节点从 `prevStateRoot` 出发：
- 确定性重放执行配方：在同一规则/排序下，对批次数据进行逐条执行与聚合（无并发状态冲突），得到 `replayNextStateRoot`。
- 约束检查：
  - 资金守恒：资产总量与账户余额变更相匹配（不可凭空造币/消失）。
  - 最优成交与时间优先：**重放结果的成交集合**与撮合规则一致，不得违反价格优先/时间优先；可通过对 `ordersRoot` 的有序展开和 `auditLog` 的到达顺序证明。
  - 合规校验：限价/市价越界、滑点/风控参数、账户风险（保证金/杠杆/风险分数）等。
- 数据可用性：
  - 批次数据必须可下载、可验证（CID 与 Merkle 根一致）。
  - 若数据不可用或校验失败，则进入挑战/仲裁流程，阻止最终性。
- 最终比较：`replayNextStateRoot` 必须与 `BatchCommit.nextStateRoot` 一致。若不一致即视为作弊或错误。

### 防止节点/序列器作弊的制度与技术措施
- 质押与惩罚（Slashing）：序列器/撮合引擎运行需抵押质押。出现以下行为触发惩罚：
  - 批次承诺与重放的状态根不一致（不实承诺）。
  - 数据不可用或拒绝提供批次原始数据。
  - 违反价格-时间优先、公平撮合与风控不变量。
- 多重见证与阈值签名：
  - 多个独立观察者/审计节点对批次进行见证，并对 `BatchCommit` 进行阈值签名；链上仅接受达到阈值的承诺。
  - 降低单点序列器作弊风险。
- 挑战窗口与交互式争议解决：
  - 在 `CHALLENGE_WINDOW` 内任何验证者可提交挑战证明（如提供反例：存在订单在公平规则下应成交却未成交）。
  - 通过交互式证明游戏（逐步二分定位）或直接重放证明判定胜负，败者触发惩罚。
- 不可抵赖的审计日志：
  - 入口层对每个订单返回用户签名的接收凭证（Receipt），并计入 `auditLogRoot`；任何“漏单/插队”都能够通过凭证与时间序列审计追溯。
- TEE（可信执行环境）与远程证明（可选增强）：
  - 撮合引擎运行在 TEE（如 SGX/SEV）；每次批次附带远程证明 `quote`（度量值），验证节点核验“确为指定版本的撮合代码”。
  - 防止引擎私改规则、插队或暗箱操作；与挑战机制形成双重防线。
- 数据可用性与备份：
  - 批次数据写入内容寻址存储（IPFS/Blob）与多副本节点；提供带带宽保证的分发层，避免“选择性拒绝服务”。
- 经济激励一致性：
  - 保留 `gasPrice`/费用排序在链上结算层，以鼓励优质订单与稳定参与。

### TEE/MPC 等高级选项（取舍）
- TEE：优点是能在硬件层提供“规则未被篡改”的强证明；缺点是硬件信任根与生态复杂度。
- MPC/多方见证：不同方共同参与撮合/签名，增加抗作恶强度；但延迟与工程复杂度更高。
- 推荐策略：主路径采用“可重放+挑战+质押惩罚”，在高价值场景叠加 TEE 远程证明或多方见证增强。

## 小额支付与交易型场景优化
- 状态/支付通道：用户之间开通双边或多边通道，微支付在通道内累积，周期性与批次一起结算到链上。
- 乐观微批：对小额支付与低风险订单采用“快速确认+异步深度核验”，在出现风险信号时自动进入挑战与冻结。
- 分层队列与快车道：
  - 正常交易走标准队列；低风险小额支付/做市订单走快车道；可动态切换。
  - 拥塞时优先维持系统安全与公平，降级非关键路径。

## 自适应风控与限流（入口与链上联动）
- 分层校验：轻量签名与重复/Nonce/黑名单校验在入口；深度风控在撮合/验证重放阶段完成。
- 自适应限流：根据队列水位与安全告警动态调整每地址/每 IP/每账户的速率（令牌桶/漏桶）。
- 可疑交易缓行：对命中可疑特征的订单进入“观察队列”，异步评分后决定是否加入批次。

## 关键参数建议（可根据压测与风控调优）
- `CHALLENGE_WINDOW`: 1–3 秒（本地/单机测试可设为 0.5–1 秒）。
- `MICROBATCH_INTERVAL`: 50–100 ms；`MAX_ORDERS_PER_BATCH`: 5k–20k。
- `DATA_AVAILABILITY_REPLICAS`: ≥3；入口回执（Receipt）保留 24–48 小时。
- `SECURITY_MODE`: `strict`/`balanced`/`perf_eval` 三档，根据场景切换。
- `SLASHING_RULES`: 承诺不一致、数据不可用、违反撮合公平、不变量失败时按比例罚没质押。

### 伪代码示例：验证节点重放
```ts
type BatchCommit = {
  batchId: string;
  prevStateRoot: string;
  nextStateRoot: string; // claimed
  ordersRoot: string;
  matchesRoot: string;
  balanceDiffsRoot: string;
  auditLogRoot: string;
  cid: string; // content address for full batch data
  producerSig: string; // sequencer signature
  witnessSigs?: string[]; // optional threshold witnesses
};

function validateOffchainBatchCommit(commit: BatchCommit): ValidationResult {
  const batchData = fetchByCID(commit.cid); // must be available
  if (!verifyMerkleRoots(batchData, commit)) return fail("Merkle roots mismatch");

  const state = loadState(commit.prevStateRoot);
  const replayResult = replayExecutionRecipe(state, batchData.recipe);

  if (!checkInvariants(replayResult)) return fail("Invariant violation");
  if (replayResult.nextStateRoot !== commit.nextStateRoot) return fail("State root mismatch");

  // optional: fairness checks using auditLog and arrival order
  if (!checkPriceTimePriority(batchData)) return fail("Fairness violation");

  return ok();
}
```

## 监控与审计
- 指标：入口 TPS、批次大小、挑战频率、数据可用性延迟、失败原因分布、质押惩罚统计。
- 审计：每日生成批次审计报告（订单到达序列、成交配对、公平性证明采样）；保留原始回执与批次数据的可检索索引。

## 风险与权衡
- 去中心化 vs 性能：集中式序列器提高吞吐，但需质押、可审计、挑战与惩罚来弥补信任缺口。
- 体验 vs 最终性：亚秒级入口响应与数秒级最终性之间的权衡；对不同业务设置差异化策略。
- 数据可用性：必须确保任何批次在挑战窗口内可被完整下载与重放，否则拒绝最终性。

## 演练与测试建议
- 压测两类指标：
  - “入口 TPS”（订单接收/撮合吞吐）。
  - “链上 TPS”（批次验证/结算吞吐）。
- 演练作弊场景：
  - 承诺不一致、漏单/插队、数据不可用、违反不变量；验证挑战与惩罚是否生效。
- 安全回归：
  - 在 `SECURITY_MODE=strict` 下确保所有风控/限流/挑战逻辑完整。
  - 在 `perf_eval` 下评估极限吞吐并观察风控告警与降级行为。

## 结论与后续
- 通过“链下高性能撮合 + 链上确定性重放与挑战惩罚”的架构，可以在不牺牲安全与公平的前提下，获得接近 Hyperliquid 的吞吐与延迟表现。
- 关键在于：
  - 执行配方可重放、数据可用、审计日志不可抵赖。
  - 挑战窗口与经济惩罚保障反作弊；必要时叠加 TEE/MPC 增强。

## 全链共享流动性（链下撮合协同）
- 全局订单簿与对等共享：
  - 定义全局 `PairID = hash(base, quote, market_config)` 与 `LiquidityProviderID`；所有接入方（交易所、DApp、做市商）以统一对等协议发布/订阅订单与流动性元数据。
  - 撮合引擎维护“全局聚合订单簿”，按价格-时间优先生成批次，并对每个订单来源保留不可抵赖的回执与到达序列（计入 `auditLogRoot`）。
- 流动性承诺与证明：
  - 每个批次承诺包含 `liquidityMetaRoot`（LP 列表/配额/路由来源）、`ordersRoot`、`matchesRoot`、`balanceDiffsRoot` 等；验证节点在重放时校验“来源公平性与配额规则”。
  - 引入“路由选择公平性”检查：对相同价格档的多来源订单进行抽样，验证未出现偏置（如单来源长期优先）。
- DA 与跨域同步：
  - 批次数据在多副本 DA 网络分发（≥3 区域），接入方可独立构建审计视图；观察者进行阈值见证降低单点操控风险。
- 经济一致性：
  - 使用统一费率与结算基准（TTN/ttUSD），并在批次承诺中附带 `feeReceiptsRoot`，便于后续多方分账与审计。

## 共享流动性的三层手续费分成机制
- 分层目标：让协议、基础设施安全参与者、实际供给流动性的主体都能获得可量化、可审计的收益分成。
- 三层结构（建议初始比例，可配置）：
  - L1 协议与安全基础层（20–40%）
    - 协议金库（运营/研发）、验证者区块生产奖励、挑战者奖励池、观察者见证补贴。
  - L2 路由/生态与接入层（10–30%）
    - 路由器/聚合器、推荐/渠道、跨域入口运营方；按实际贡献的有效订单量与质量分配。
  - L3 流动性提供层（40–70%）
    - 做市商/LP 按成交量加权（maker/taker）与库存风险承担度分配；支持对冲补贴与库存修正参数。
- 结算与证明：
  - 批次承诺写入 `feeReceiptsRoot`（逐笔费用、来源、层级、比例）与 `distributionPlanRoot`（聚合分账计划）。
  - 链上执行“分账结算交易”将费用划转至各层账户或金库；挑战窗口内可对分配不公提出证明。
- 动态调整与防刷：
  - 对低质量流量（高撤单比/低成交）与异常路由进行降权或拒绝；对 LP 的“刷量”行为通过库存风险参数与价格影响模型惩罚。
  - 观察者定期输出“公平性采样报告”，治理层可按投票调整各层比例与参数。

## 交易与原生代币 0 Gas 上链方案（TTN / ttUSD）
- 核心原则：用户侧零 Gas；系统侧 Gas 成本由批次费用与赞助池覆盖，链上保持可审计与反滥用能力。
- 机制组成：
  - 赞助池（Sponsor Pools）：在 `SEQUENCER_CONFIG` 中定义赞助账户与预算；批次承诺附带 `gasCostRoot` 与赞助扣减计划。
  - 费用回收：订单成交费用优先充入赞助池或协议金库，用于覆盖验证者 Gas 成本；周期性进行“赞助再平衡结算”。
  - 白名单类型：
    - 交易撮合批次（批次承诺交易与结算）。
    - 原生 TTN/ttUSD 的简单转账、通道充值/结算、DApp 内部转账（限速与上限）。
  - 降级与熔断：异常拥塞或攻击情况下自动切换为“限速 0 Gas”或“要求最小 Gas”，保障系统稳定与安全。
- 与现有 Zero-Gas 引擎的衔接：
  - 在 `blockchain/core/zero-gas-engine.ts`/`zero-gas-manager.ts` 扩展类型白名单与赞助池扣费逻辑；将 `gasCostRoot` 与 `sponsorAccountsRoot` 纳入批次承诺。
  - `transaction-pool.ts` 中对 0 Gas 交易设置更严格的限流与可疑行为缓行策略；异常时自动切换到普通交易路径。
- 约束与风控：
  - 每账户/每对资产的 0 Gas 转账设定日/小时上限与风险评分阈值；高风险账户要求最小 Gas 或延迟审查。
  - ttUSD 的稳定性与铸赎流程需与金库/储备管理绑定，保证资金守恒与审计可得。

## 运行建议（初始参数）
- `MICROBATCH_INTERVAL`: 50–100ms；`BLOCK_TIME`: 1–2s；`CHALLENGE_WINDOW`: 2s。
- `MAX_ORDERS_PER_BATCH`: 5k–20k；每块承载 3–10 个批次（随负载动态）。
- 分成比例示例（V1）：`feeSplit = { L1: 30%, L2: 20%, L3: 50% }`；可根据治理调整。
- 0 Gas 白名单：撮合批次、TTN/ttUSD 简单转账与通道操作；限速与上限按风险评分动态调节。

## 区块最佳大小（S_opt）与动态调整算法
- 目标：在给定 `BLOCK_TIME` 下，最大化吞吐同时保证“传播 + 下载校验 + 重放 + 投票 + 挑战窗口”按时完成。
- 预算划分（建议）：
  - 传播预算（P）：区块时间的 20–30%。
  - 下载与校验（D）：区块时间的 30–40%。
  - 重放（R）：区块时间的 20–30%。
  - 投票与挑战（V）：区块时间的 10–20%。
- 动态算法（简化）：
  - 设微批平均大小 `B_avg`（订单数或指令数）、每批重放耗时 `t_replay`、传播耗时估计 `t_gossip`；当 `P+D+R+V <= BLOCK_TIME` 且安全告警低时提升每块批次数或 `MAX_GAS_LIMIT`；否则降低。
  - S_opt 近似满足：`t_gossip(S_opt) + t_download(S_opt) + t_replay(S_opt) + t_vote <= BLOCK_TIME - t_challenge_reserve`。
- 建议区间：
  - `BLOCK_TIME = 1–2s` 时，每块 3–10 个批次、`MAX_GAS_LIMIT = 30–50M`（结合指令成本与节点硬件调优）。
  - 拥塞或高挑战频次时，自动下调至 2–5 批次或 20–30M Gas。

## 区块分层验证设计（分层验证）
- 层级定义：
  - L0（头部/承诺层）：仅校验区块头、批次承诺存在性与阈值见证签名有效。
  - L1（数据可用性层）：并行下载批次数据，校验 Merkle 根一致与到达序列审计日志可用。
  - L2（快速重放层）：对执行配方进行快速重放与不变量检查，比较 `nextStateRoot` 一致性；交易进入“预确认”。
  - L3（深度验证层）：在挑战窗口内对随机采样或可疑批次执行“全量公平性验证”（价格-时间公平、路由抽样）；如发现问题触发挑战与回滚/重算。
- 协议动作：
  - 预确认（Pre-Commit）：L0+L1 通过后标记批次为可结算候选。
  - 提交（Commit）：L2 完成且无即时错误，进入提交候选；观察者见证达阈值。
  - 最终性（Finalize）：挑战窗口 `CHALLENGE_WINDOW` 过后未被成功挑战且投票通过，进入最终性；失败则惩罚与重算。
- 取舍：
  - L2/L3 的分层验证保证性能与安全平衡；在 `SECURITY_MODE=strict` 下扩大 L3 比例与范围，在 `perf_eval` 下缩小 L3 以测吞吐上限。

## 共享流动性分层（40% / 50% / 10%）与结算细则
- 目标分成（V2，按你提出的比例）：
  - 流动提供方（LP/MM）：40%。
  - 交易发生方（Trader/Order Side）：50%（可分 Maker/Taker 比例，例如 Maker 30%、Taker 20%，按市场微调）。
  - 平台支持我方：10%（含协议金库、验证者与挑战奖励池的保留比例，具体在平台内部二次分配）。
- 承诺与结算：
  - 在批次承诺中写入 `feeReceiptsRoot`（逐笔费用归属）与 `distributionPlanRoot`（分账计划）。
  - 结算交易执行按 V2 比例划转：
    - `LP/MM` 依据成交量与库存风险参数加权；防刷与风险修正。
    - `Trader` 按成交方向与订单类型（Maker/Taker）发放返利；异常账户降权或冻结。
    - `Platform 10%` 内部再分：建议至少 3–5% 用于验证者与挑战奖励池，剩余进入协议金库与观察者补贴。
- 防刷与公平性：
  - 设置“撤单比/滑点/价格影响”阈值，对恶意流量降权或剔除；观察者出具公平性报告，治理按投票调整参数。
- 配置示例（V2）：
  - `feeSplitV2 = { liquidityProviders: 40, traders: 50, platform: 10 }`。
  - `traderSplit = { maker: 30, taker: 20 }`（总和=50）；`platformAllocation = { validators_challenge_pool: 3–5, treasury_and_observers: 5–7 }`（总和=10）。
